# 工作手册

## 公开研究

1. 明确问题和决策编号，优先官方公开来源。
2. 记录 URL、日期和适用市场；产品源码固定 cn 提交。
3. 区分页面承诺、代码可见实现和生产验证；记录反例及未知。
4. 只摘录完成判断必需的信息，不存个人信息或敏感配置。
5. 将结果放入 reports，更新策略与实验卡中的假设。

## 提案到执行

1. Dot（Growth Manager） 填 [实验模板](../experiments/template.md)。
2. 检查 [审批门](../OPERATING_RULES.md)，将具体问题列入决策清单。
3. 所有者批准具体范围；额外对外行动独立批准。
4. Cloud Codex 从持久任务卡接手明确范围；本次仅文档，记录阻塞和证据。
5. 对照 [验收](../evals/acceptance.md)，记录未完成验证和停止原因。

## 每周复盘

用 [周报](../reports/weekly-template.md) 同时写支持与反对证据，区分工作产出与业务结果。没有执行实验就写“未执行”。建议继续／调整／停止必须说明依据和下一步批准事项。

## 可恢复任务流水

唯一入口：[报告／任务索引](../reports/README.md)，当前卡 FGH-001。Dot 创建稳定 ID、范围、优先级、验收需求和决策链接；Cloud Codex 接手后记录状态、阻塞、下一行动和证据／PR；Dot 验收后交本地 Technical Lead 独立复核并按权限合并；合并后记录新基线与验证。

每次停止前更新卡，避免只在聊天保存状态。新会话先读取任务卡及其决策、证据、PR 和验收链接，核对远端 head 与范围，记录独立恢复时间、身份、识别的下一行动和核查结果。冲突或缺证据标阻塞，不猜测完成。完成卡不得删历史。

同会话读取仅证明持久内容可读，不能证明跨会话恢复通过。FGH-001 已获独立新会话恢复结果回报；这是恢复能力检查，不等于正式 Technical Lead 复审，结果和证据限制见任务卡。
