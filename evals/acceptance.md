# 首版验收清单

## 文档质量

- 五个必需根文件齐全，六个目录有实质内容且被 Git 跟踪。
- 30 天计划覆盖四周及收尾，角色、依赖、审批门和停止规则明确。
- 业务指标有定义；基线、目标及样本未证实则标记待建立／待审批。
- 重要事实附来源；事实、假设、建议分开；代码与生产状态分开。
- 所有 Markdown 相对链接及锚点可解析；外部来源可访问或记录例外。
- 两份独立研究集成；若缺失，记录阻塞并保持草稿。

## 权限与公开安全

- diff 仅包含本仓库文档；无软件、CI、部署、埋点或营销执行。
- 无凭据、个人简历、个人资料、敏感运营配置、虚构业绩或效果保证。
- 产品 cn 只读；默认分支未修改、未合并。

## 首次草稿提交验证（一次性）

- 确认分支、基线与完整 diff；保留 LICENSE。
- 检查远端分支 SHA 等于预期提交；PR head SHA 一致。
- PR 指向正确基线且为 draft，无自动合并。
- 报告确切分支、提交、PR URL、检查结果及未完成验证。

## 主张反例检查

“所有数据只在本地”“已验证完整支付”“保证 ATS／录用提升”“已有增长基线”若缺证据，一律不通过。示例不等于真实案例，内部评审不等于用户验证。

## 每个任务的交付验收

1. 从[任务入口](../reports/README.md)获取稳定 ID、owner／executor、获批范围、预期、阻塞和下一行动。
2. 逐项比较预期与实际，检查对应文件／来源／PR diff，不把文件存在等同任务完成。
3. 对每项记录已完成、进行中、待审批、阻塞或未验证及失败边界；研究、代码、生产、PDF、截图各自区分。
4. 核实范围外操作未发生；失败时按任务回滚计划处理。本次文档可由后续更正／回退 PR 撤回，不强推或改 main；产品／生产未改故无生产回滚。
5. 收尾证据：变更清单、链接与 diff 检查、远端 head、服务关闭、未完成项及下一负责人。最终 SHA 在 PR 和交付消息核对，不让本提交自引用未生成 SHA。
6. Technical Lead 以新会话从 FGH-001 卡独立定位六项修订和验收证据，报告识别的下一行动、复核 head 与结论。未执行则明确“独立跨会话恢复未验证”。同会话 readback 不可标通过。

常态 Harness 文档交付由 Dot 验收，Technical Lead 独立 Review、验证并合并达标 PR；初稿 draft 检查不构成永久停留规则。当前修订明确保持 Draft，Cloud Codex 不 ready、不 merge、不 resolve。
